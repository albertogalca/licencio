### Key Findings

- **Critical Issues**: 0 findings requiring immediate attention. No injection, authentication bypass, IDOR or remote code execution vector was found.
- **OWASP Top 10 Compliance**: 3/10 categories fully compliant (A03 Injection, A06 Vulnerable Components, A10 SSRF); the remaining seven are Partial with no Non-Compliant category.
- **Overall Security Score**: 72/100

The two High findings are both in the money path and both reachable by an unauthenticated attacker:

1. **H-001** — the renewal-price guard in `Product#create_checkout_session` tests only that `renew_license_key` is *non-blank*, never that it names a real license. Passing any string buys a brand-new full license at the discounted renewal price. This defeats the exact attack the guard's own comment says it exists to stop.
2. **H-002** — the Stripe webhook fulfills `checkout.session.completed` without checking `session.payment_status`, and never handles `checkout.session.async_payment_failed`. Any delayed-notification payment method issues a permanent license before the money settles, with no revocation path.

Everything else is defence-in-depth. The codebase is unusually well reasoned about security: seat races are held under `with_lock`, webhook idempotency is enforced by unique database indexes, login codes are peppered and compared with `secure_compare`, magic-link tokens carry 256 bits of entropy and a 30-minute expiry, CSP forbids inline script and style, and both Brakeman and bundler-audit report zero findings.

### High Risk Findings

#### H-001: Renewal-price guard accepts any non-blank license key, selling full licenses at the renewal discount

**Location**: `app/models/product.rb:176`
**Risk Score**: 7.4 (High)
**Pattern Detected**: Business-logic authorization check that validates the *presence* of a parameter instead of its *validity*. The parameter is fully attacker-controlled from a public, unauthenticated URL.
**Code Context**:

```ruby
# app/models/product.rb:173-178
    # The renewal price is a discount for people who already bought — /api/checkout takes any
    # price_id belonging to this product, so without this guard anyone could buy a brand-new
    # license at the renewal rate.
    if renewal_stripe_price_id.present? && price.id == renewal_stripe_price_id && renew_license_key.blank?
      raise CheckoutNotConfigured, "#{slug} renewal price is not for sale on its own"
    end
```

`renew_license_key` arrives unvalidated from the query string:

```ruby
# app/controllers/api/checkouts_controller.rb:40-45
    def checkout_session
      Product.find_by!(slug: params[:product_slug]).create_checkout_session(
        price_id: params.require(:price_id), email: params[:email],
        renew_license_key: params[:renew_license_key],
        client_reference_id: params[:client_reference_id], ref: params[:ref])
    end
```

and fulfillment silently falls through to issuing a *new* license when the key does not resolve:

```ruby
# app/models/license.rb:145-154
      existing = renew_key && product.licenses.find_by(license_key: renew_key)
      # Renew only a license the payer already owns, or an unclaimed (imported) one the payer now
      # claims — never let a client-supplied renew_key renew someone else's license.
      if existing && (existing.customer_id.nil? || existing.customer_id == customer&.id)
        # Renewals never credit an affiliate — affiliate_id/commission_cents intentionally dropped.
        existing.renew!(stripe_payment_id:, price_id:, buyer: customer)
      else
        product.issue_license!(customer:, quantity:, stripe_payment_id:, price_id:,
          stripe_customer_id:, amount_cents:, currency:, update_policy:, affiliate_id:, commission_cents:)
      end
```

**Impact**: An unauthenticated attacker sends `GET /api/checkout?product_slug=picmal&price_id=<renewal_price_id>&renew_license_key=x`. The guard passes because `"x"` is not blank. Stripe charges the renewal rate. On `checkout.session.completed`, `find_by(license_key: "x")` returns `nil`, `existing` is falsy, and the `else` branch mints a **brand-new full license** with the full seat count from the price metadata. The same works with a *valid* license key belonging to someone else: the ownership check fails, and the `else` branch mints a new license anyway. The renewal price is by design the cheapest SKU on the product (`app/models/product.rb:142-144` excludes it from `variants` precisely because it would otherwise win the cheapest-variant tiebreak), so the loss is the full delta between the new-license price and the renewal price on every sale, for as long as the URL circulates. The `price_id` values are not secret — they appear in `GET /api/products/:slug/variants` responses and in any buy-button URL.

The existing test at `test/models/product_test.rb:200-203` asserts this behaviour rather than catching it: it passes the literal string `"PICM-1"` and asserts the session is created.

**Recommendation**: Resolve the key to a license that is actually renewable, and reject otherwise. See "Code Remediation Examples" below. Harden the fulfillment side in the same change, so that a `renew_key` that fails to resolve to a renewable, payer-owned license aborts rather than falling through to `issue_license!`.
**Fix Priority**: Immediate

#### H-002: Stripe webhook fulfills sessions whose payment has not settled, with no failure path

**Location**: `app/controllers/webhooks/stripe_controller.rb:11-17`
**Risk Score**: 7.6 (High)
**Pattern Detected**: State-transition validation gap. The handler treats `checkout.session.completed` as proof of payment; Stripe emits it for delayed-notification payment methods before funds settle, with `payment_status` set to `unpaid`.
**Code Context**:

```ruby
# app/controllers/webhooks/stripe_controller.rb:10-26
    case event.type
    when "checkout.session.completed"
      session = event.data.object
      License.fulfill_from_stripe_session(product, session)
      # The unlock flow is opted into per price, by a `tier` in its metadata, and lives
      # alongside the license it just minted — the same sale grants both. A price with no
      # tier (picmal's) records nothing.
      Purchase.record_stripe!(product, session, price: product.session_price(session))
    when "charge.refunded"
      charge = event.data.object
      # Full refunds only revoke the license; partial refunds — and uncaptured charges, where
      # both amounts are 0 — leave it active.
      if charge.amount_captured.to_i.positive? && charge.amount_refunded == charge.amount_captured
        License.refund!(product:, stripe_payment_intent: charge.payment_intent)
        Purchase.refund!(product:, provider_order_id: charge.payment_intent)
      end
    end
```

`session.payment_status` is never read — not here, and not in `License.fulfill_from_stripe_session` (`app/models/license.rb:65-111`) or `Purchase.record_stripe!` (`app/models/purchase.rb:47-65`). There is no `when "checkout.session.async_payment_failed"` branch and no `when "checkout.session.expired"` branch.

**Impact**: Checkout is created with `managed_payments: { enabled: true }` (`app/models/product.rb:190`), which lets Stripe present the full set of locally relevant payment methods. Several of those — SEPA Direct Debit, Bacs Direct Debit, boleto, OXXO, Klarna and other buy-now-pay-later rails — are delayed-notification methods. For those, Stripe fires `checkout.session.completed` immediately with `payment_status: "unpaid"`, then later fires `checkout.session.async_payment_succeeded` or `checkout.session.async_payment_failed`. This code fulfills on the first event: it mints an active license, signs an offline EdDSA entitlement token the server can never re-check (`app/models/product.rb:216-229` documents that there is no verification endpoint), records a `Purchase` row that unlocks the mobile apps forever (`app/models/purchase.rb:71-79`, deliberately no `exp`), emails the key, and credits an affiliate commission computed from `session.amount_subtotal` (`app/models/license.rb:91-92`). When the payment then fails, nothing revokes any of it, because the failure event is not handled. `charge.refunded` never fires for a payment that never succeeded. The result is a free, permanent, unrevocable license plus an affiliate commission payable on a sale that produced no money.

The same gap affects disputes — see M-005.

**Recommendation**: Gate fulfillment on `session.payment_status`, and handle the async lifecycle events. See "Code Remediation Examples" below.
**Fix Priority**: Immediate

### Medium Risk Findings

#### M-001: Affiliates can self-refer — no identity check between the referrer and the buyer

**Location**: `app/models/license.rb:90-92`
**Risk Score**: 5.5 (Medium)
**Pattern Detected**: Missing anti-fraud control on a commission-bearing workflow.
**Code Context**:

```ruby
# app/models/license.rb:87-92
    # An affiliate is credited only on a new purchase (renewals pass nothing). Commission is frozen
    # here off amount_subtotal — pre-VAT, because under Managed Payments amount_total includes tax we
    # never receive — and stored on the Payment, never recomputed from the affiliate's current rate.
    affiliate = Affiliate.find_by(id: meta[:affiliate_id]) if meta[:affiliate_id].present?
    subtotal = session.amount_subtotal || session.amount_total
    commission_cents = affiliate&.commission_for(subtotal, percent: product.affiliate_commission_percent)
```

The affiliate is credited purely from session metadata. Neither `Affiliate#email` nor `Affiliate#payout_email` is ever compared against `session.customer_details.email`, and nothing marks a `Payment` as self-referred.

**Impact**: An approved affiliate appends `?ref=<own-code>` to their own purchase and earns the commission (default 20%, `db/schema.rb:49`) back on it — a standing personal discount. Scaled up, this becomes a grey-market resale channel: the affiliate buys licenses at an effective 20% off and resells below the storefront price, and the studio pays for the privilege. Because commission is frozen on the `Payment` at sale time and payouts are reconciled from `Payment.payable` (`app/models/payment.rb:14-15`), the only control is an operator noticing the pattern by eye on the `Admin::AffiliatesController#show` page.

**Recommendation**: Record the buyer's normalized email on the `Payment` at fulfillment time and exclude self-referred sales from the `payable` scope:

```ruby
# app/models/affiliate.rb
  def self_referral?(buyer_email)
    return false if buyer_email.blank?
    normalized = Purchase.normalize_email(buyer_email)
    [ email, payout_email ].compact_blank.any? { |own| Purchase.normalize_email(own) == normalized }
  end
```

Call it in `fulfill_from_stripe_session` and drop `affiliate`/`commission_cents` when it returns true, logging the attempt so repeat offenders surface.
**Fix Priority**: Within 1 month

#### M-002: Product API key stored in plaintext while every sibling secret is encrypted

**Location**: `app/models/product.rb:27-30`, `db/schema.rb:161`
**Risk Score**: 5.5 (Medium)
**Pattern Detected**: Inconsistent encryption-at-rest coverage. The one credential left unencrypted is the one that grants the widest API access.
**Code Context**:

```ruby
# app/models/product.rb:27-30
  encrypts :loops_api_key
  encrypts :eddsa_private_key
  encrypts :stripe_secret_key
  encrypts :stripe_webhook_secret
```

```ruby
# db/schema.rb:161
    t.string "api_key", null: false
```

```ruby
# app/controllers/api/base_controller.rb:7-10
    def authenticate_product
      @product = Product.find_by(api_key: request.headers["X-Api-Key"])
      render_api_error(:unauthorized) unless @product
    end
```

`student_discount_code` (`db/schema.rb:190`) is likewise plaintext.

**Impact**: `ActiveRecord::Encryption` is deployed and working for four columns, so the threat model already assumes database contents can be exposed independently of the application (a leaked backup, a managed-Postgres snapshot, a read replica, a `pg_dump` in a support ticket). In that scenario the Stripe keys, Loops key and the EdDSA signing key stay protected, but `products.api_key` reads out in the clear. That key authenticates `POST /api/licenses/activate` (mint trials, activate any license key, and read the licensee's name and email back — `app/controllers/api/activations_controller.rb:45-48`), `DELETE /api/licenses/deactivate` (free any device's seat) and `POST /api/licenses/recover` (send a portal magic link to any address). Encryption here is cheap: the column is looked up by exact value, which is exactly what deterministic encryption supports.

**Recommendation**: Add `encrypts :api_key, deterministic: true` and `encrypts :student_discount_code`, then re-encrypt existing rows with `bin/rails db:encryption:encrypt` or a one-off migration. `Product.find_by(api_key:)` continues to work unchanged under deterministic encryption.
**Fix Priority**: Within 1 month

#### M-003: The six-digit unlock code is written to production logs

**Location**: `config/initializers/filter_parameter_logging.rb:6-8`
**Risk Score**: 4.8 (Medium)
**Pattern Detected**: Incomplete `filter_parameters` coverage over an authentication credential.
**Code Context**:

```ruby
# config/initializers/filter_parameter_logging.rb:6-8
Rails.application.config.filter_parameters += [
  :passw, :email, :secret, :token, :_key, :crypt, :salt, :certificate, :otp, :ssn, :cvv, :cvc
]
```

The parameter carrying the unlock credential is named `code`, which matches none of these:

```ruby
# app/controllers/v1/unlocks_controller.rb:62
      result = code.verify!(params[:code].to_s.strip)
```

**Impact**: `ActionController::LogSubscriber` logs the `Parameters:` line at `info`, and `config/environments/production.rb:41` runs at `info` by default. Every `POST /v1/unlock/verify` therefore writes the live six-digit code to STDOUT, where Coolify or the container runtime persists it. The code is the sole credential in the unlock flow: with it and the matching address, an attacker mints a permanent, offline-verified entitlement token that this server can never revoke (`app/models/purchase.rb:71-79`). The `email` param is filtered, but the code alone plus a known customer address is enough, and the address is recoverable elsewhere. Codes live for ten minutes (`app/models/login_code.rb:7`), so the exposure window is short but recurring, and log retention makes it durable. Secondary gaps in the same list: `hardware_id` (a stable device fingerprint sent on every activation) and `ref` (affiliate attribution) are also unfiltered.

Note the credential is correctly protected everywhere else — it is peppered with `secret_key_base`, stored only as a SHA-256 digest, and compared with `ActiveSupport::SecurityUtils.secure_compare` (`app/models/login_code.rb:28-29,47`). The logger is the single leak.

**Recommendation**:

```ruby
Rails.application.config.filter_parameters += [
  :passw, :email, :secret, :token, :_key, :crypt, :salt, :certificate, :otp, :ssn, :cvv, :cvc,
  :code, :hardware_id, :ref
]
```

`:code` is a substring filter and will also cover `login_code`, `discount_code` and `student_discount_code`. Verify that no view or log line renders `params[:code]` for debugging before deploying.
**Fix Priority**: Within 1 week

#### M-004: Two secret-gated endpoints have no rate limiting

**Location**: `app/controllers/v1/support_controller.rb:4-6`, `app/controllers/api/admin/base_controller.rb:5-11`
**Risk Score**: 5.2 (Medium)
**Pattern Detected**: Shared-secret authentication with no guess budget, on endpoints that disclose PII or mutate bulk state.
**Code Context**:

```ruby
# app/controllers/v1/support_controller.rb:4-9
class V1::SupportController < Api::PublicController
  before_action :authenticate_support

  def lookup
    product = Product.find_by(slug: params[:product_slug]) or return render_api_error(:product_not_found)
    purchases = Purchase.for_email(product, params[:email]).order(:purchased_at)
```

```ruby
# app/controllers/api/admin/base_controller.rb:5-11
    def authenticate_admin
      provided = request.authorization.to_s.remove(/\ABearer /)
      key = ENV["ADMIN_API_KEY"].to_s
      unless key.present? && ActiveSupport::SecurityUtils.secure_compare(provided, key)
        head :unauthorized
      end
    end
```

Neither controller declares `rate_limit`. Every other externally reachable controller in the application does — checkouts (20/min), activations (30/min), products (30/min), validations (5/min), students (5/min), recoveries (5/min), renewals (5/min), affiliate signup and recovery (5/min), admin sessions (10/3min), unlock request (10/hour) and unlock verify (10/min).

**Impact**: `POST /v1/support/lookup` returns, for any email address, every purchase row for a product including `email`, `tier`, `purchased_at`, `updates_until`, `refunded_at`, `platforms`, `provider` and `provider_order_id` (`app/controllers/v1/support_controller.rb:30-32`) — a bulk customer-PII enumeration primitive. It also re-sends unlock codes past the per-address budget (lines 13-15). `POST /api/admin/migrations/import` writes licenses in bulk from an unbounded request body. Both are gated only by an environment-variable secret. `env.example:33,39` documents generating them with `openssl rand -hex 32`, but nothing enforces length or entropy, no rotation exists, failures are not logged or alerted, and with no throttle an attacker gets unlimited attempts against whatever value was actually set. The comparison itself is correctly timing-safe, which is the harder half; the missing half is the budget.

The migrations endpoint also accepts an arbitrarily large body with no size cap, since `CSV.parse(request.body.read, headers: true)` (`app/controllers/api/admin/migrations_controller.rb:15`) buffers the whole payload into memory.

**Recommendation**: Add `rate_limit to: 10, within: 1.minute, with: -> { head :too_many_requests }` to `V1::SupportController` and `rate_limit to: 5, within: 1.minute` to `Api::Admin::BaseController`. Log every authentication failure on both (`Rails.logger.warn`) so brute-force attempts are visible in Sentry breadcrumbs, and assert a minimum secret length at boot so a short or empty-adjacent token fails loudly instead of silently.
**Fix Priority**: Within 1 week

#### M-005: Disputes and partial refunds never revoke a license or reverse a commission

**Location**: `app/controllers/webhooks/stripe_controller.rb:18-25`
**Risk Score**: 5.0 (Medium)
**Pattern Detected**: Incomplete state-transition coverage on the payment lifecycle. Money can leave without the entitlement following it.
**Code Context**:

```ruby
# app/controllers/webhooks/stripe_controller.rb:18-25
    when "charge.refunded"
      charge = event.data.object
      # Full refunds only revoke the license; partial refunds — and uncaptured charges, where
      # both amounts are 0 — leave it active.
      if charge.amount_captured.to_i.positive? && charge.amount_refunded == charge.amount_captured
        License.refund!(product:, stripe_payment_intent: charge.payment_intent)
        Purchase.refund!(product:, provider_order_id: charge.payment_intent)
      end
```

There is no `when "charge.dispute.created"` or `when "charge.dispute.funds_withdrawn"` branch.

**Impact**: A chargeback pulls the money back through the card network without ever emitting `charge.refunded`. The license stays `active`, the `Purchase` row stays `live`, the offline entitlement token stays valid forever, and `Payment.payable` (`app/models/payment.rb:14-15`) still counts the commission because it filters only on `licenses.status = "refunded"`. The studio therefore loses the sale price, keeps serving the product, and pays an affiliate 20% on it. Card-testing and friendly-fraud rings target exactly this pattern. The partial-refund case is a deliberate, documented choice and is defensible on its own; the dispute case appears to be an oversight rather than a decision, since no comment addresses it.

**Recommendation**: Handle the dispute events through the existing, already-idempotent revocation path:

```ruby
    when "charge.dispute.created", "charge.dispute.funds_withdrawn"
      dispute = event.data.object
      License.refund!(product:, stripe_payment_intent: dispute.payment_intent)
      Purchase.refund!(product:, provider_order_id: dispute.payment_intent)
```

`License.refund!` already no-ops on an already-refunded license (`app/models/license.rb:120`) and `Purchase.refund!` is scoped to `live` (`app/models/purchase.rb:69`), so a dispute that later resolves in the studio's favour can be reversed by hand in admin without the redelivery causing duplicate refund emails.
**Fix Priority**: Within 1 month

#### M-006: Admin console is single-factor with no session expiry and no account lockout

**Location**: `app/controllers/admin/sessions_controller.rb:4-18`, `app/models/admin_user.rb:1-7`
**Risk Score**: 6.0 (Medium)
**Pattern Detected**: Weak session and authentication controls on the highest-privilege surface in the system.
**Code Context**:

```ruby
# app/controllers/admin/sessions_controller.rb:4-18
  rate_limit to: 10, within: 3.minutes, only: :create,
    with: -> { redirect_to new_admin_session_path, alert: "Too many attempts. Try again in a few minutes." }

  def new
  end

  def create
    if admin = AdminUser.find_by(email: params[:email])&.authenticate(params[:password])
      reset_session
      session[:admin_user_id] = admin.id
      redirect_to admin_root_path
    else
      redirect_to new_admin_session_path, alert: "Invalid email or password."
    end
  end
```

```ruby
# app/models/admin_user.rb:1-7
class AdminUser < ApplicationRecord
  has_secure_password

  normalizes :email, with: ->(e) { e.strip.downcase }

  validates :email, presence: true, uniqueness: true
end
```

`has_secure_password` gives bcrypt hashing and a timing-safe comparison, and `reset_session` on login correctly prevents session fixation. But there is no second factor, no password-strength validation, no per-account lockout (the 10-per-3-minutes limit keys on IP, so a distributed attempt resets it), no absolute or idle session timeout, and no `config/initializers/session_store.rb` — sessions are browser-lifetime cookies that never expire server-side.

**Impact**: This one credential controls everything: all customer PII (`Admin::CustomersController`), license minting and status changes (`Admin::LicensesController`), Stripe secret keys and webhook secrets for every product (`Admin::ProductsController`), affiliate commission rates and approvals, and the payout ledger. A single phished or reused password, or a stolen session cookie from an unattended machine, yields permanent uncontested access — there is nothing to expire and nothing to step up against. There is also no audit trail: no model records which admin minted a license, changed a commission rate or recorded a payout, so an intrusion leaves no forensic record.

**Recommendation**: Three changes, in order of value. First, add an absolute session lifetime so a stolen cookie ages out — store `session[:admin_authenticated_at]` on login and expire it in `require_admin`. Second, add TOTP as a second factor (`rotp` is a small, well-audited gem and fits `has_secure_password` alongside a `otp_secret` column encrypted with `encrypts`). Third, add an `AdminAuditLog` model written from `Admin::BaseController` recording `admin_user_id`, controller, action, and the affected record id, so privileged actions are attributable.
**Fix Priority**: Within 1 month

#### M-007: Student discount is one shared static code behind a weak domain gate

**Location**: `app/models/academic_email.rb:14`, `app/jobs/student_discount_job.rb:19`
**Risk Score**: 4.5 (Medium)
**Pattern Detected**: A gate that authorizes access to a *shareable* secret, so a single bypass devalues it permanently.
**Code Context**:

```ruby
# app/models/academic_email.rb:12-25
  # The country code is capped at two letters on purpose: {2,3} would also swallow
  # edu.com and ac.net.
  PATTERN = /\.(edu|ac)(\.[a-z]{2})?\z/

  def self.match?(email)
    parts = email.to_s.strip.downcase.split("@", -1)
    return false unless parts.size == 2

    local, domain = parts
    return false if local.empty? || domain.empty? || domain.include?("..")
    return false unless domain.match?(/\A[a-z0-9.-]+\z/)

    domain.match?(PATTERN)
  end
```

```ruby
# app/jobs/student_discount_job.rb:16-22
        data: {
          discount_code: product.student_discount_code,
          pricing_url: product.checkout_cancel_url,
          product_name: product.name,
          sender_email: product.sender_email
```

`student_discount_code` is a single scalar column (`db/schema.rb:190`), not a per-request generated code.

**Impact**: Two compounding weaknesses. First, the regex accepts any domain ending in `.ac` — Ascension Island's ccTLD, which is sold openly to anyone by commercial registrars with no accreditation check. **Fix Priority**: Within 2 months

#### L-001: Host authorization silently disables itself when `APP_HOST` is unset

**Location**: `config/environments/production.rb:84`
**Risk Score**: 3.5 (Low)
**Pattern Detected**: A security control guarded by a conditional that fails open.
**Code Context**:

```ruby

```

**Impact**: The comment asserts `APP_HOST` is required, but nothing enforces it. #### L-002: Rate-limit keys derive from `request.remote_ip` with no `trusted_proxies` configured

**Location**: `config/environments/production.rb:28`, and every `rate_limit` declaration
**Risk Score**: 3.5 (Low)
**Pattern Detected**: Throttle identity taken from a header-derived value whose trust boundary is not pinned in configuration.
**Code Context**:

```ruby
# config/environments/production.rb:27-28
  # Assume access is through a TLS-terminating reverse proxy (Coolify/Render/Kamal proxy/etc).
  config.assume_ssl = true
```

No `config.action_dispatch.trusted_proxies` is set anywhere in `config/`. Every limiter relies on Rails' default key:

```ruby
# app/controllers/api/checkouts_controller.rb:3
  rate_limit to: 20, within: 1.minute, with: -> { head :too_many_requests }
```

`ActionController::RateLimiting` defaults to `by: -> { request.remote_ip }`.

**Impact**: `remote_ip` is computed by `ActionDispatch::RemoteIp` from `X-Forwarded-For`, discarding entries that fall in the default trusted set (loopback, RFC1918, link-local, unique-local). The deployment is explicitly behind a TLS-terminating proxy on what is almost certainly a private Docker network, so the proxy hop is discarded as trusted and the effective key comes from the forwarded chain. This is safe **only if** the proxy appends the real client IP to any client-supplied `X-Forwarded-For` rather than passing one through — which Traefik, Caddy and Cloudflare all do correctly by default. If the proxy is ever reconfigured to trust an inbound `X-Forwarded-For`, or replaced with one that does, every per-IP limiter in the application becomes trivially evadable by rotating a header value: unlimited admin password guesses, unlimited license-key probing against `/portal/renewals/new` and `/api/licenses/validate`, and unlimited mail bombing through the recovery and student endpoints. The exposure is a deployment property that the application does not currently pin.

**Recommendation**: Set `config.action_dispatch.trusted_proxies` in `config/environments/production.rb` to the actual proxy range, so the trust boundary is declared in code rather than inherited from a default:

```ruby
  config.action_dispatch.trusted_proxies = ActionDispatch::RemoteIp::TRUSTED_PROXIES +
    [ IPAddr.new(ENV.fetch("TRUSTED_PROXY_CIDR", "10.0.0.0/8")) ]
```

For the two highest-value limiters — admin login and unlock verify — consider keying on the submitted identifier as well as the IP, so a single account cannot be ground down from many source addresses.
**Fix Priority**: Within 2 months

## Architecture Security Assessment

### Authentication & Authorization Analysis

- **Four independent authentication schemes, each correctly scoped to its surface.** The product API key (`X-Api-Key`, `app/controllers/api/base_controller.rb:8`) gates the desktop licensing endpoints; customers authenticate by product-scoped magic link (`PortalToken`) or six-digit login code (`LoginCode`); affiliates by magic link (`AffiliateToken`); admins by bcrypt password session. Two shared-secret env tokens gate the support lookup and the bulk import. No scheme leaks into another's surface, and `session[:customer_id]`, `session[:affiliate_id]` and `session[:admin_user_id]` are distinct keys read only by their own base controller.
- **Session management is sound.** `reset_session` is called before establishing identity in all three session-based logins (`portal/sessions_controller.rb:6`, `affiliate/sessions_controller.rb:6`, `admin/sessions_controller.rb:13`), closing session fixation. `Affiliate::BaseController#current_affiliate` re-checks `approved` on every request (`app/controllers/affiliate/base_controller.rb:10`), so revoking an affiliate takes effect immediately rather than at next login — a detail that is easy to get wrong. The gap is lifetime: no session carries an absolute expiry (M-006).
- **Token entropy and lifecycle are appropriate.** `PortalToken` and `AffiliateToken` both use `SecureRandom.urlsafe_base64(32)` — 256 bits — with a 30-minute expiry, a unique index on `token`, and `where(expires_at: Time.current..)` applied *before* `find_by(token:)` so an expired token can never authenticate. The deliberate choice to make them reusable within the window rather than single-use is correct and well argued: mail scanners and link preloaders would otherwise burn one-shot tokens before the human clicks. `LoginCode` is the one low-entropy credential (10^6), and it is defended in exactly the right place — a hard five-attempt budget incremented *before* any other check so an aborted connection still spends it (`app/models/login_code.rb:37-38`), a ten-minute TTL, retirement of prior codes on reissue, and a per-address budget of three codes per fifteen minutes enforced in `V1::UnlocksController#over_code_budget?`.
- **Timing-safe comparison is applied where it matters.** `ActiveSupport::SecurityUtils.secure_compare` guards the login-code hash (`app/models/login_code.rb:47`), the support token (`app/controllers/v1/support_controller.rb:24`), the admin API key (`app/controllers/api/admin/base_controller.rb:8`) and both halves of the App Review unlock (`app/controllers/v1/unlocks_controller.rb:96-98`). `has_secure_password` covers the admin password. The remaining `==`-equivalents are all indexed database lookups on high-entropy values — `find_by(api_key:)`, `find_by(token:)`, `find_by(license_key:)` — where the timing signal from a B-tree probe is not a practical oracle against a 256-bit token or a UUID-based license key. Stripe webhook signatures are verified by `Stripe::Webhook.construct_event`, which uses the SDK's own constant-time comparison plus a 300-second timestamp tolerance.
- **No IDOR was found.** Every user-supplied identifier that reaches a `find_by` is either scoped to an ownership boundary or belongs to an admin-only action. `Portal::ActivationsController#destroy` is the sharpest example, scoping by both product and customer before `find_by(id: params[:id])` (`app/controllers/portal/activations_controller.rb:4-5`). `Api::ActivationsController` scopes license lookup through `@product.licenses`, so an API key for one product cannot touch another's licenses. `Portal::DashboardController` scopes to `current_product.licenses.where(customer: current_customer)`.
- **Mass assignment is correctly controlled on every write.** All six `create`/`update` paths use `params.require(...).permit(...)` with explicit column lists. Two deserve credit: `Admin::ProductsController#product_params` (`app/controllers/admin/products_controller.rb:39-53`) makes `slug`, `bundle_identifier` and `license_prefix` settable only on create because they are baked into issued license keys, and drops blank secret fields so an edit cannot accidentally clear a stored Stripe key. `Affiliate::SignupsController` force-merges `status: "pending"` and omits `commission_percent`, so a public applicant cannot self-approve or set their own rate. The one `to_unsafe_h` in the codebase (`app/controllers/api/admin/migrations_controller.rb:17`) is safe because `License::Importer#import_row` assigns an explicit column list rather than splatting the hash.
- **CSRF protection is correct throughout.** `ApplicationController < ActionController::Base` inherits `default_protect_from_forgery` from `config.load_defaults 8.1`, and no controller calls `skip_forgery_protection`. Every `skip_before_action` in the codebase targets `require_customer`, `require_affiliate` or `require_admin` on a deliberately public action — never a forgery check. The API and webhook controllers descend from `ActionController::API`, which is the right base for token-authenticated, cookie-less endpoints.
- **The `renewals_controller.rb` decision to skip `require_customer` is defensible.** Treating the license key as a bearer secret is the right call for this flow: the renewal link must survive being read days after the 30-minute magic-link token died, and the worst an attacker with someone else's key can do is *pay to extend it*. The controller is rate-limited to 5/min, the price is chosen server-side by `License#renewal_price_id` (never from params), and `License#renewable?` gates on policy, status and expiry window. The one leak is that `new` confirms whether a key exists, which the rate limit is explicitly there to blunt. This is a sound trade-off — and it stands in useful contrast to H-001, where the equivalent key check on the *public* checkout path was never actually implemented.

### Data Protection Analysis

- **Encryption at rest is deployed but not complete.** `ActiveRecord::Encryption` protects `loops_api_key`, `eddsa_private_key`, `stripe_secret_key` and `stripe_webhook_secret` (`app/models/product.rb:27-30`) — correctly including the EdDSA private key, which is the single most consequential secret in the system since it signs entitlement tokens that no server ever re-verifies. `products.api_key` and `products.student_discount_code` are left plaintext (M-002). Customer PII (`customers.email`, `customers.name`, `purchases.email`) is plaintext by necessity — `Purchase.for_email` matches through a normalized-email expression index that deterministic encryption could not support in its current form.
- **Input validation is thorough on the paths that need it.** `Product::HEX_COLOR` and `Product::HTTP_URL` validate branding at the model layer, and `Product#brand_style` re-checks the hex format at render time before interpolation (`app/models/product.rb:75,86`) — belt-and-braces on a value that lands in a `<style>` block. `AcademicEmail.match?` rejects malformed and `..`-containing domains before its pattern test. `License.fulfill_from_stripe_session` ignores an unrecognised `update_policy` from price metadata rather than letting a bad enum string raise and wedge fulfillment on Stripe's retries (`app/models/product.rb:104-105`).
- **Output encoding leaves no XSS surface.** Zero uses of `raw`, `html_safe`, `<%==` or `sanitize` across all 27 templates and the single helper. The one dynamic style injection is defended twice: `tag.style` HTML-escapes its content, and `<style>` is a raw-text element where entities are not decoded, so even a hostile value could not break out — and `brand_style` re-validates against `HEX_COLOR` before emitting anything. Brakeman's `CrossSiteScripting`, `ContentTag` and `SafeBufferManipulation` checks are all clean.
- **No injection vector of any kind was found.** Every raw SQL fragment in the codebase passes user input as a bound parameter: `Product.matching` (`app/models/product.rb:60`), `License.search`, `Customer.search`, `Purchase.for_email` (`app/models/purchase.rb:40`, where the interpolated `NORMALIZED_EMAIL_SQL` is a frozen constant and the value is bound), `License.expire_overdue!` and the admin affiliate search. No `order(params[...])`, no Ransack, no dynamic finders, no `eval`, no `send` with user input, no shell execution anywhere in `app/` or `lib/`. `Stripe::Price.retrieve(price_id, ...)` takes a fully attacker-controlled id, but the SDK applies `CGI.escape` when building the resource URL (verified in `stripe-19.3.0/lib/stripe/api_resource.rb:92`), so path traversal into another Stripe endpoint is not possible, and `Stripe::InvalidRequestError` is caught and downgraded to a client error.
- **The two `redirect_to ... allow_other_host: true` triage notes in `config/brakeman.ignore` are both correct** — re-verified independently rather than trusted. There are in fact three such call sites, all safe. `api/checkouts_controller.rb:17` and `portal/renewals_controller.rb:19` redirect to `checkout_session.url`, a Stripe Checkout Session URL created server-side moments earlier and never derived from a request parameter. `api/checkouts_controller.rb:34` redirects to `Product#checkout_cancel_url`, an admin-set database column; the request only chooses *which product's* URL via `params[:product_slug]`, and every candidate value is one the studio configured. No user-supplied string reaches a redirect target anywhere in the application. `redirect_back` at `admin/activations_controller.rb:9` gets further protection from `raise_on_open_redirects`, on by default under `load_defaults 8.1`.

## Technical Recommendations

### Immediate Code Fixes

1. **Validate the renewal license key, not just its presence (H-001).** In `Product#create_checkout_session`, resolve `renew_license_key` to an actual license on this product and confirm `renewable?` before allowing the renewal price. Harden the fulfillment side too: in `License.fulfill!`, a `renew_key` that fails to resolve should abort rather than silently minting a full new license.
2. **Gate fulfillment on settled payment and handle the async lifecycle (H-002).** Check `session.payment_status == "paid"` before calling `License.fulfill_from_stripe_session`, add a `checkout.session.async_payment_succeeded` branch that runs the same fulfillment, and add `checkout.session.async_payment_failed` so an unsettled sale is never left as a live entitlement.
3. **Add `:code` to `filter_parameters` (M-003).** One line, closes a live authentication credential leaking into production logs. Add `:hardware_id` and `:ref` in the same change.

### Security Enhancements

1. **Rate-limit the two shared-secret endpoints and log their auth failures (M-004).** `V1::SupportController` and `Api::Admin::BaseController` are the only externally reachable controllers without a limiter, and both are high-value. Add a boot-time assertion on minimum secret length.
2. **Encrypt `products.api_key` deterministically (M-002).** `encrypts :api_key, deterministic: true` preserves `find_by(api_key:)` and closes the one credential a database-only compromise would hand over intact. Encrypt `student_discount_code` at the same time.
3. **Handle `charge.dispute.*` through the existing revocation path (M-005).** Four lines in the webhook `case`, reusing `License.refund!` and `Purchase.refund!`, both already idempotent.
4. **Block affiliate self-referral (M-001).** Compare the normalized buyer email against the affiliate's `email` and `payout_email` at fulfillment, drop the commission when they match, and log the attempt.
5. **Make student discount codes single-use (M-007).** Generate a per-address Stripe promotion code with `max_redemptions: 1` instead of mailing one shared constant, and tighten `AcademicEmail::PATTERN` to reject bare `.ac`.

### Architecture Improvements

1. **Give the admin console an absolute session lifetime, a second factor, and an audit trail (M-006).** These three together convert the highest-privilege surface from "one password forever" into something with a recovery story. The audit trail is the highest value per unit of effort — without it, an intrusion leaves no record of which licenses were minted or which commission rates were changed.
2. **Pin the trust boundary for client IP in configuration (L-002).** Set `config.action_dispatch.trusted_proxies` explicitly so every rate limiter in the application stops depending on an undeclared property of the deployment. Consider keying the admin-login and unlock-verify limiters on the submitted identifier as well as the IP.
3. **Make configuration fail fast rather than fail open (L-001).** `config.hosts << ENV.fetch("APP_HOST")` without the guard turns a silently disabled security control into a startup error.
4. **Add the missing database constraints that the application logic already assumes (L-003, L-004).** A partial unique index on active activations per device, and a uniqueness constraint plus an owed-amount validation on payouts. The codebase already handles `ActiveRecord::RecordNotUnique` gracefully in `Customer.upsert!` and `License.fulfill!` — this extends the same pattern to the two places still relying on check-then-act.

```ruby
  def create_checkout_session(price_id:, email:, renew_license_key: nil, client_reference_id: nil, ref: nil)
    if checkout_success_url.blank? || checkout_cancel_url.blank?
```

```ruby
      # A session tagged as a renewal must renew or do nothing. Falling through to issue_license!
```

### Gating fulfillment on settled payment (references H-002)

**Before (Vulnerable)**:

```ruby
# app/controllers/webhooks/stripe_controller.rb:10-26

    when "checkout.session.completed"

      License.fulfill_from_stripe_session(product, session)

```

**After (Secure)**:

```ruby
# app/controllers/webhooks/stripe_controller.rb
    case event.type
    # Delayed-notification methods (SEPA/Bacs debit, boleto, BNPL) fire completed BEFORE the money
    # settles, with payment_status "unpaid". Fulfilling there mints a license and signs an offline
    # token this server can never re-check, and async_payment_failed would arrive too late to matter.
    when "checkout.session.completed", "checkout.session.async_payment_succeeded"
      session = event.data.object
      fulfill(product, session) if session.payment_status.in?(%w[paid no_payment_required])
    # The sale never settled. Idempotent — a redelivery finds nothing left to revoke.
    when "checkout.session.async_payment_failed", "checkout.session.expired"
      session = event.data.object
      License.refund!(product:, stripe_payment_intent: session.payment_intent || session.id)
      Purchase.refund!(product:, provider_order_id: session.payment_intent || session.id)
    when "charge.refunded"
      charge = event.data.object
      if charge.amount_captured.to_i.positive? && charge.amount_refunded == charge.amount_captured
        License.refund!(product:, stripe_payment_intent: charge.payment_intent)
        Purchase.refund!(product:, provider_order_id: charge.payment_intent)
      end
    # A chargeback pulls the money back without ever emitting charge.refunded, so the license and
    # the affiliate's commission would both survive a sale that produced nothing.
    when "charge.dispute.created", "charge.dispute.funds_withdrawn"
      dispute = event.data.object
      License.refund!(product:, stripe_payment_intent: dispute.payment_intent)
      Purchase.refund!(product:, provider_order_id: dispute.payment_intent)
    end
    head :ok
  rescue Stripe::SignatureVerificationError
    head :bad_request
  end

  private
    def find_product = Product.find_by(id: params[:product_id])

    def fulfill(product, session)
      License.fulfill_from_stripe_session(product, session)
      Purchase.record_stripe!(product, session, price: product.session_price(session))
    end
```

**Security Impact**: Closes the window in which an unsettled payment produces a permanent, unrevocable entitlement. `License.fulfill!` already returns early on a duplicate `stripe_payment_intent` (`app/models/license.rb:143`), so routing `async_payment_succeeded` through the same path is idempotent when Stripe delivers both events. The dispute branch also stops affiliate commissions accruing on charged-back sales, since `Payment.payable` filters on `licenses.status = "refunded"`.

## Summary

This security analysis identified **0 critical**, **2 high**, **7 medium**, and **8 low** risk vulnerabilities across the codebase. The analysis focused on code patterns, dependency vulnerabilities, and configuration security.

**Key Strengths Identified**:

- **No injection surface of any kind.** Every raw SQL fragment binds its parameters, there is no dynamic ordering or Ransack-style search, no `eval`/`send`/shell execution, and zero uses of `raw`, `html_safe` or `<%==` across all 27 templates. Both Brakeman and bundler-audit are clean, and both gate CI.
- **Webhook integrity is genuinely well built.** Per-product signature verification means an event signed with one product's secret can only reach that product's licenses. Idempotency rests on real unique database indexes rather than application checks, so Stripe's at-least-once delivery and its 300-second replay window are both absorbed structurally.
- **The seat-limit race — the one that would mint free capacity — is correctly closed.** `License#activate!` holds the license row under `with_lock` for the whole check-and-create, and `renew!` does the same. This is the concurrency bug that most licensing systems ship with, and it is not present here.
- **Credential handling is careful and consistent.** 256-bit magic-link tokens with expiry filtered *before* lookup; a login-code attempt budget spent before any other check so an aborted connection still costs a guess; `secret_key_base` peppering so a database dump yields no working codes; `secure_compare` on every low-entropy secret; `reset_session` on all three logins.
- **Deliberate anti-enumeration design.** The unlock request endpoint answers identically and at constant time whether or not an address ever bought anything, with the purchase lookup pushed into a background job specifically so no caller can time it. The recovery endpoints and the affiliate approval flow follow the same discipline.
- **Supply chain is tight.** 21 direct gems from a single source, no git or path gems, no npm tree at all, SHA-256 checksums for every gem in `Gemfile.lock`, `BUNDLE_DEPLOYMENT=1`, weekly Dependabot on two ecosystems, a non-root multi-stage container, and no secret ever committed to any branch in the repository's history.
- **The code documents its own threat reasoning.** Comments consistently explain *why* a control exists and what it is defending against, which made this audit faster and will make the next one faster still. H-001 is the notable exception where the comment describes a control the code does not fully implement — which is exactly the case for keeping the practice.

**Critical Areas Requiring Immediate Attention**:

- **H-001 — the renewal-price guard is bypassed by any non-blank string.** The comment above it states precisely the attack it exists to prevent, and the check does not prevent it. An unauthenticated GET on a public URL buys a full license at the discounted renewal rate, and an existing test asserts the vulnerable behaviour rather than catching it. Fix the guard and the test together.
